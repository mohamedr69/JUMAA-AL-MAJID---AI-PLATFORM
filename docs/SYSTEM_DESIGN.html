1Deployment topology

Two processes, started together by start.bat. There is no API gateway, no BFF and no server-side rendering: the browser talks straight to uvicorn across an origin boundary, which is why CORS and cookie settings matter as much as they do.

2The ASGI layer: how bytes become a Python call

This is the part usually hand-waved. uvicorn is a single-threaded event loop; the FastAPI endpoints in this codebase are almost all plain def. The handoff between those two facts is the most important mechanical detail in the system.

#ComponentWhat happens to the request
1OS socketuvicorn, port 8000 The event loop accepts the TCP connection. Nothing is parsed yet — only bytes have arrived.
2HTTP protocol parserh11 / httptools Request line, headers and body are parsed incrementally. A malformed request dies here with a 400 that no application code ever sees.
3ASGI scope builtuvicorn protocol layer A dict: type: "http", method, path, raw_headers, query_string, client. The body is not in it — it is pulled later through the receive callable, which is how a large upload streams instead of buffering.
4The app is calledmain.py:100 uvicorn awaits app(scope, receive, send). app is the FastAPI instance, a subclass of Starlette. From here everything is a coroutine on that one event loop.
5Middleware stack, outermost firstmain.py:102–190 Starlette wraps the app in each registered middleware. Registration order is inside-out: the last @app.middleware declared sits closest to the router. Effective order here: CORS → request_id → slide_session → router.
6Routingstarlette.routing The path is matched against the route table built by the 25 include_router calls (main.py:191–242). First match wins, so prefix collisions matter: /projects is claimed by nine different routers. No match → 404 without touching the database.
7Dependency resolutionfastapi.dependencies FastAPI walks the endpoint signature and builds the dependency graph before calling the handler: path params coerced, query params validated, the Pydantic body model constructed, Depends(get_db) and Depends(get_current_user) executed. A failure here is a 422 and the handler is never entered.
8The threadpool handoffanyio worker thread The critical hop. The endpoint is a sync def, so FastAPI does not await it — it runs it via run_in_threadpool on an anyio worker thread (40 by default). The event loop stays free to accept other requests. Everything the handler does — blocking SQLite I/O, reading a PDF off OneDrive, shelling out to AutoCAD — happens on that worker thread, never on the loop.
9The handler runsapp/routers/*.py Router code calls services; services call the ORM. See traces A–G.
10Serializationresponse_model= The returned ORM object or dataclass is validated and filtered through the declared Pydantic model, then JSON-encoded. This is the field filter: a User row goes out as UserOut, so hashed_password cannot leak.
11Unwindreverse middleware order Dependency teardown (get_db closes the session in its finally) → slide_session may re-issue the cookie → request_id writes the log line and stamps the header → CORS adds its headers → send → bytes on the socket.
Sync vs async, counted. Across the 25 routers exactly four handlers are async def: ifc_boq.py:477, ifc_boq.py:494, their shared helper ifc_boq.py:337, and submittal.py:854 — every one of them a handler that must await an UploadFile. All the rest are sync, and therefore threadpooled. Three consequences follow directly: the engine needs check_same_thread: False (database.py:13); shared in-process state needs real locks (_fill_lock, design.py:77; _start_lock, verification.py:35); and an async handler that wants to do blocking work must hand it back to a thread itself with run_in_threadpool (ifc_boq.py:486).

4Trace A — POST /auth/login

The canonical trace: an unauthenticated request that ends with a session cookie. Every hop below is real code, not a sketch.

#ComponentWhat happens
1SPAlib/api.ts request("/auth/login", { method: "POST", body: JSON.stringify({email, password}) }) with credentials: "include" and Content-Type: application/json. Because of the content type the browser first sends an OPTIONS preflight.
2CORS preflightmain.py:102 OPTIONS /auth/login is answered by the middleware alone: allowed origin, methods, headers, Allow-Credentials: true. No router, no dependency, no database.
3uvicorn → ASGI The real POST is parsed by h11, turned into a scope, and app(scope, receive, send) is awaited.
4request_idmain.py:124 Assigns request.state.request_id and starts the duration timer. It also peeks at the cookie to attribute the log line — on login there is none yet, so user: null.
5slide_sessionmain.py:156 Passes straight through on the way in. On the way out it returns early because the path starts with /auth/ — login must own its own Set-Cookie.
6Route matchauth.py:16,21 APIRouter(prefix="/auth") + @router.post("/login") → the login function. No auth dependency on this route — it is the one that creates the session.
7Validation + sessionschemas.py / database.py:66 The JSON body is parsed into LoginRequest (a malformed body is 422 here). Depends(get_db) opens a SessionLocal.
8Threadpool login is a sync def → run on an anyio worker thread. bcrypt is deliberately slow; this is exactly why it must not run on the event loop.
9Handler: lookupauth.py:22 db.query(User).filter(User.email == payload.email.lower()).first() → SQLAlchemy compiles SELECT ... FROM users WHERE email = ?, the pooled DBAPI connection executes it, the row is mapped to a User in the identity map.
10Handler: gatesauth.py:24–46 In order: unknown email → generic 401 (never "no such user"); locked_until in the future → 423 with minutes remaining; is_active false → 403; then verify_password (security.py:16, passlib/bcrypt).
11Handler: failure pathauth.py:41 A wrong password increments failed_login_attempts; at MAX_FAILED_LOGIN_ATTEMPTS it sets locked_until = now + LOCKOUT_MINUTES and resets the counter. db.commit() runs before the 401 is raised — the lockout must survive the rejection.
12Handler: success pathauth.py:48–56 Counter cleared, locked_until = None, last_login_at = now, db.commit(), db.refresh(user), then activity.record(db, user, "auth.login", ...) writes a row into activity_events — after the work succeeded, never before.
13Tokensecurity.py:22 create_access_token(subject=str(user.id), role=user.role.value) → HS256 JWT with sub, role, exp, signed with SECRET_KEY.
14Cookieauth.py:59 response.set_cookie(httponly=True, samesite="lax", secure=COOKIE_SECURE, max_age=30*60, path="/"). httpOnly is the point: the token is never readable by JavaScript, so an XSS bug cannot steal it.
15Serializationresponse_model=UserOut The User ORM object is filtered to UserOut. hashed_password, failed_login_attempts and locked_until are simply not in the model, so they cannot be sent.
16Unwind get_db closes the session → slide_session no-ops on /auth/ → request_id logs {"route": "/auth/login", "status": 200, "ms": 214, "user": null} and sets X-Request-ID → CORS headers → response.
17Back in the SPAcontext/AuthContext.tsx The browser stores the cookie; the JSON user is put in AuthContext. ProtectedRoute and RoleRoute now let the app render. Every later request carries the cookie automatically.
Note the asymmetry. The token is created and signed on the server, and the SPA never sees it. The client's copy of "who am I" is only the UserOut JSON, which is advisory — the server re-decodes the cookie on every subsequent request. Client-side role checks are UI convenience; deps.py is the enforcement.

Where a read gets its data from — three different sources

The database

Project rows, BOQ lines, systems, submittals. The default.

The filesystem

The archive folder (_project_folder, design.py:88) and the company library. Read live, on the worker thread, which is why a stale OneDrive mount surfaces as 503 rather than a hang.

A cache table

result_cache, the datasheet index under .cache/, and the ep_archive_folders index — so a search is a query, not a directory walk.

6Trace C — versioned write: PUT /projects/{id}

Two engineers can have the same project open. A write therefore has to say which version it was made against. This is the optimistic-concurrency path, and it runs on the BOQ, project info, design inputs and compliance statements alike.

7Trace D — long work: POST /projects/{id}/jobs/boq-reread

Re-reading a four-page scanned Design Sheet takes a minute or more. Run inside the request, the page could only spin, a refresh lost the answer, and there was no stopping it. The answer is a job row: the request returns 202 immediately and the work continues on a thread of its own.

#ComponentWhat happens
1Handler, in the requestjobs.py:66 require_role(*CREATOR_ROLES) → _get_project_or_404 → refuse if the project has no Design Sheets (409) → _refuse_duplicate (jobs.py:57) returns 409 job_running with the existing job's id if one is already queued or running for this project and kind.
2The closurejobs.py:77 A local work(session, ctx) is defined. It captures only ids — project_id, user_id — never the ORM objects from the request's session. Those belong to a session that is about to close.
3Job rowservices/jobs.py:70 jobs.start(...) inserts a background_jobs row: status="queued", progress={done:0,total:0,message:"Waiting to start"}, and commits it, so the row exists before the response leaves.
4Thread launchservices/jobs.py:81 A threading.Thread is started running run(), which opens its own SessionLocal(). This is the point people get wrong: the request's session and the job's session are two different sessions on two different connections, and the request's is closed the moment the response is sent.
5Responsejobs.py:88 202 Accepted with the JobOut body. The request is over; the work has barely begun.
6The workerservices/jobs.py:83 status="running", started_at set and committed, then work(session, JobContext(job_id)) runs — here boq_candidates.build, which reads the sheets, calls the AI reader and writes a candidate BOQ.
7Progressservices/jobs.py:38 ctx.progress(done, total, message, **extra) opens yet another short-lived session, writes the progress JSON and commits, then closes it. A separate session on purpose: progress must become visible to the polling request even though the job's own long transaction is still open.
8Cancellationservices/jobs.py:38,53 The same read that writes progress also reads cancel_requested; if set, it raises Cancelled. So a job stops between steps — at the next page, never mid-write.
9Completionservices/jobs.py:87 status="succeeded", result (the candidate id and a summary), finished_at. On an exception the traceback is stored in error and the status is failed.
10Pollinglib/useJob.ts → jobs.py:130 The page polls GET /jobs/{id} — an ordinary authenticated read of one row — and renders JobProgress. A refresh loses nothing: the job is found again by id.
11Stopjobs.py:139 POST /jobs/{id}/cancel only sets the flag. The worker notices it at its next checkpoint.
A job that was running when the server stopped cannot be resumed. On the next start, jobs.fail_interrupted (services/jobs.py:124, called from the lifespan at main.py:70) marks every still-running row as failed with that reason — so no page waits forever on work that died with the process.

Endpoints that follow this pattern

jobs/boq-reread and jobs/documents-intake (jobs.py), jobs/ai-verify (verification.py), and ifc-drawings/jobs (ifc_boq.py:494), which additionally reports a percentage, a stage name and an estimated seconds-remaining through the same progress channel.

8Trace E — upload: POST /projects/{id}/ifc-drawings

The only place in the codebase where the async/sync distinction is visible in the source, and the clearest illustration of why the threadpool exists.

#ComponentWhat happens
1SPAcomponents/ifc/api.ts A FormData POST. The browser sets multipart/form-data with its own boundary — the client must not set Content-Type itself.
2ASGI body streaming The body is not in the scope. Starlette pulls it in chunks through receive, spilling to a temporary file past a size threshold, so a 60 MB DWG does not sit in memory as one string.
3The async handlerifc_boq.py:477 async def upload_drawing(...) — declared async because it must await the upload. It runs on the event loop, not on a worker thread.
4Await the bytesifc_boq.py:337 await _received(file) → filename, extension and the bytes. Awaiting yields control, so other requests keep being served while the upload arrives.
5Back to a threadifc_boq.py:486 await run_in_threadpool(lambda: _read_drawing(...)). Everything blocking — converting DWG to DXF through AutoCAD's core console or the ODA converter, parsing with ezdxf, matching blocks against ifc_symbols, writing rows — happens on a worker thread. Without this one call the event loop would freeze for the whole conversion and the entire server would stop answering.
6Failureifc_boq.py:488 A ReadError becomes 422 with the reason. A missing converter is refused up front with an instruction to install AutoCAD or the ODA converter, or to upload a DXF instead (ifc_boq.py:511).
7Or, as a jobifc_boq.py:494 The tab actually uses the sibling endpoint, which does steps 3–4 in the request and then hands the parsed bytes to trace D, so the page can show a stage and an ETA rather than a spinner.

Where uploaded bytes land

Never in the archive. UPLOADS_ROOT (default backend/uploads, or <DATA_ROOT>/uploads when a data root is set, config.py) gets a folder per project; _save_upload (projects.py:1152) writes the file and the path is stored on the row. The platform reads the OneDrive archive and writes only to its own uploads folder — a deliberate one-way boundary.

11Startup and shutdown

Before the first request can be served, the lifespan context manager (main.py:41–97) runs in strict order. Anything slow enough to make a new machine wait is pushed onto a background thread instead.

Config is resolved once, at import. get_settings() is @lru_cached (config.py), and its model_validators run then: ~ and %VARS% expanded, the OneDrive archive located by name (find_synced_folder), Tesseract found on the PATH or where the installer puts it, and DATA_ROOT rewritten into DATABASE_URL, UPLOADS_ROOT, CACHE_ROOT and BACKUPS_ROOT. A wrong value in .env therefore shows up at start, not mid-request — with one exception: an AI budget set too low is only discovered when a call is actually made.

What holds the whole thing together

One place per concern

Auth in deps.py. Versioning in concurrency.py. Long work in services/jobs.py. Model calls in provider.py. Config in config.py. Each is small enough to read in one sitting, and nothing routes around them.

Fail visibly, not silently

Migrations run at startup; interrupted jobs are failed on boot; a stale write is refused rather than merged; an AI answer is a proposal, not a write; a document that cannot be read says "Not read: why".

Read wide, write narrow

The archive and the company library are read; only the platform's own database and UPLOADS_ROOT are written. That one-way boundary is why a sync conflict can never destroy project data.
